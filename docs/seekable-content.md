# Encrypted file streaming and seeking

New encrypted `writeContent` output uses the existing OBSENC02 segmented format. Each one-MiB block authenticates its ordinal, final path and encrypted header, which declares the complete byte count and SHA-256 digest. Every block has a derived key and a new GCM nonce. A partial read authenticates the header and each requested block before releasing that block. It does not verify unrequested blocks; full verification still checks every block and the complete digest. Existing OBSENC01 files retain full-file authentication before partial output. They are not silently converted by reading them.

Sources with an authenticated expected size and digest are written directly. Already-buffered input derives that declaration in bounded hash batches, yielding to cancellation and other event-loop work. It does not make an additional disk pass. Both paths verify the actual stream against the declaration before publication.

For unknown streams, the temporary file initially holds independently encrypted blocks under a provisional header. Only internal finalization uses that provisional descriptor; it is never published as retained content. Once streaming establishes the real size and digest, finalization reads and authenticates one block at a time, then re-encrypts it under a fresh final header, salt, derived key and nonce. It writes the final header after those blocks. It never retags old ciphertext with a reused GCM nonce. Temporary finalization uses the same file and bounded memory, including for short last blocks; it does not need a second complete copy or plaintext staging.

That compatibility-preserving strategy costs one extra encrypted read/write pass at intake for unknown streams. Later seeks read only the requested blocks. Measurements must report both intake cost and playback amplification on the intended storage; local synthetic results are not NAS throughput guarantees. Progress names the finalization stage explicitly. Known-hash and buffered input avoid that pass.

Success still requires the caller's completion check, a stable unlocked key, file sync, close and atomic replacement with the platform's supported directory barrier. Finalization, capacity, cancellation or key-retirement failures preserve the previous destination and clean up the temporary file. A killed process can leave only its private temporary, which the owning operation's existing recovery cleanup handles. No new persistent envelope or catalogue generation is introduced. Power-loss and physical storage-interruption guarantees retain the limitations in [Filesystem durability](filesystem-durability.md).
